# Cryptographic specification

This document specifies the algorithms, keys, formats and procedures that protect
secrets in SecretShare, and records where the implementation differs from the
initial design. The control write-up is WEB-3 in `docs/security/security-controls.md`.

State assessed: branch `main`, commit `2b98875`, 23 September 2026.

---

## 1. Summary of mechanisms

| Purpose | Mechanism | Parameters | Implemented in |
|---|---|---|---|
| Secret content encryption | AES-GCM | 256-bit key, 96-bit random IV, 128-bit tag, no additional authenticated data | `web/lib/crypto.ts::encryptAesGcm` |
| Content key wrapping | RSA-OAEP | 2048-bit modulus, public exponent 65537, SHA-256 (hash and MGF1), no label | `web/lib/crypto.ts::encryptAesKeyWithRsa` |
| Browser randomness | `crypto.getRandomValues` | Browser CSPRNG | `web/lib/crypto.ts` |
| Payload identifier | `secrets.token_urlsafe(32)` | 256 bits from the operating system CSPRNG, 43 base64url characters | `api/app/core/ids.py` |
| Access tokens | JWT signed by Keycloak | RS256; verified against the realm JWKS | Keycloak; `api/app/core/auth.py` |
| Web session | Auth.js encrypted JWT (JWE) | `alg: dir`, `enc: A256CBC-HS512`, key derived from `AUTH_SECRET` with HKDF | `next-auth` 5.0.0-beta.32 |
| User passwords | Keycloak password hashing | Keycloak default provider (Argon2 from Keycloak 25); not overridden in the realm | Keycloak 26.0 |
| API → Redis, API → PostgreSQL | TLS with an internal CA | RSA 4096 keys, SHA-256 signatures, 3650-day validity; protocol version from library defaults | `tls/generate.sh`, `api/app/main.py`, `api/app/db/session.py` |
| Browser → edge (previews) | TLS terminated by Tailscale Serve | Let's Encrypt certificate per preview host name | `docker-compose.preview.yml` |

## 2. Keys

| Key | Generated by | Stored in | Lifetime and rotation | Destroyed by |
|---|---|---|---|---|
| Content key K (AES-256) | Sender's browser, one per secret | Browser memory only; stored on the server only wrapped | One secret | Garbage collection after encryption or decryption |
| Device private key | Recipient's browser, on first sign-in | IndexedDB `secretshare_keystore`, store `device_keys`, record keyed by user name, as a `CryptoKey` object | Until browser data is cleared. No rotation. | Clearing browser data |
| Device public key | Same browser | PostgreSQL `device_keys.public_key`, SPKI PEM | Registering a new key of the same platform sets `revoked_at` on the previous one | Revocation only; rows are kept |
| Keycloak realm signing key | Keycloak | Keycloak database | Keycloak key rotation (manual) | Disabling the key in Keycloak |
| `AUTH_SECRET` | Operator | `.env` | Manual; rotation ends all web sessions | Replacement |
| Internal CA and server keys | `tls-init` | `tls-certs` Docker volume, mode 600, root-owned | 3650 days; regenerated only when the volume is removed | Removing the volume |

## 3. Envelope format

The sender's browser sends the following JSON body to `POST /api/secrets`:

```json
{
  "recipient_id": "<Keycloak user name>",
  "encrypted_keys": [
    {
      "device_id": "<UUID of the device key>",
      "platform": "web",
      "encrypted_aes_key": "<base64 of RSA-OAEP(PK_device, K), 256 bytes>"
    }
  ],
  "iv": "<base64 of the 12-byte IV>",
  "ciphertext": "<base64 of the AES-GCM output, including the 16-byte tag>",
  "ttl_seconds": 600
}
```

- Binary values are encoded as standard base64 with padding (`btoa`). The decoder
  also accepts base64url.
- Redis stores `recipient_id`, `encrypted_keys`, `iv` and `ciphertext` as JSON
  under `s:<payload_id>`; `ttl_seconds` becomes the key's expiry and is not stored
  in the envelope.
- The API limits `ciphertext` to 65 536 bytes. After base64 decoding and removal of
  the tag, the largest plaintext is 49 136 bytes of UTF-8.
- The server does not decode or inspect `iv`, `ciphertext` or `encrypted_aes_key`
  (invariant 1).

## 4. Procedures

### 4.1 Device registration

1. After sign-in, the browser looks up a stored key record for the user name.
2. If none exists, it calls `generateKey` for RSA-OAEP, 2048 bits, SHA-256, and
   stores both halves in IndexedDB.
3. It exports the public key as SPKI, encodes it as PEM with 64-character lines and
   sends it to `POST /api/keys/register` with the access token.
4. The API revokes the user's active keys of the same platform, stores the new key
   and returns its `device_id`, which the browser stores with the key pair.

### 4.2 Encryption

1. The browser fetches the recipient's active public keys from
   `GET /api/keys/{user_id}`.
2. It draws K (32 bytes) and IV (12 bytes) with `crypto.getRandomValues`.
3. It encrypts the UTF-8 encoding of the plaintext: C = AES-256-GCM(K, IV, plaintext).
4. For each device j it computes Wⱼ = RSA-OAEP-SHA-256(PKⱼ, K).
5. It sends the envelope (section 3) and receives the payload identifier.

A new K is drawn for every secret, so an (K, IV) pair is never reused.

### 4.3 Decryption

1. After `POST /api/secrets/reveal` returns the envelope, the browser tries to
   unwrap each Wⱼ with its private key until one succeeds.
2. It decrypts C with K and IV. A modified ciphertext or IV fails the GCM tag check
   and produces an error instead of altered plaintext.
3. The plaintext is held in React state only; it is not written to storage.

## 5. Security properties

| Property | Holds | Condition or reason |
|---|---|---|
| Server cannot read content | Yes | The browser code is not modified (R-01) and the private key does not leave the recipient's browser. |
| Modification of ciphertext or IV is detected | Yes | GCM authentication tag. |
| Envelope is bound to its recipient | No | `recipient_id` is not authenticated data; the server can re-address an envelope, but the content remains wrapped for the original recipient's keys. |
| Recipient can verify the sender | No | Envelopes are not signed, and creation requires no authentication (R-07). |
| Sender can verify the recipient's public key | No | No fingerprint display or key pinning (R-08). |
| Forward secrecy | No | A disclosed device private key decrypts every envelope wrapped for it. Envelopes are deleted on reveal or expiry, so the exposure is limited to envelopes still stored, unless the attacker copied envelopes earlier. |
| Private key cannot be exported by scripts | No | Keys are generated with `extractable: true` (R-02). |

## 6. Deviations from the initial design

| Item | Initial design | Implementation | Consequence | Planned action |
|---|---|---|---|---|
| RSA modulus | 3072 bits | 2048 bits | About 112-bit security instead of 128-bit; within NIST SP 800-57 guidance until 2030. | Move to 3072 bits together with a format version. |
| Private key export | `extractable: false` | `extractable: true` | A script in the origin can export the key (R-02). | Generate non-extractable keys (October). |
| Format version | `v` and `alg` fields in the envelope | None | Algorithm changes cannot be distinguished from old envelopes. | Add a version field before any algorithm change. |
| Binary encoding | base64url | base64 with padding | None for security; the decoder accepts both. | None. |
| Key model | One wrapped key | One wrapped key per registered device | Supports several devices; in practice only the latest browser per platform is active. | Keep. |
