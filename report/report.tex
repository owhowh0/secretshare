\vspace{14pt}
\noindent
This internship report presents the design, theoretical foundations, architectural specification, implementation, and empirical verification of \textbf{SecretShare}, an enterprise-grade, zero-trust, ephemeral secret-sharing platform. The primary objective of the project is to resolve the acute security deficiencies of existing secret-transmission mechanisms, where confidential credentials, database passphrases, API keys, and private certificates are routinely leaked through persistent communication channels, proxy access logs, and centralized application databases. 

The developed solution establishes a rigorous zero-knowledge paradigm through client-side hybrid cryptography. Prior to network dispatch, plaintext payloads are encrypted in the sender user agent using symmetric AES-256-GCM authenticated encryption under an ephemeral content encryption key. This symmetric key is subsequently encapsulated using asymmetric RSA-OAEP 2048-bit encryption for every active cryptographic device registered by the intended recipient. Identity assertion is strictly governed by OpenID Connect and OAuth2 protocols integrated with Keycloak utilizing Proof Key for Code Exchange (PKCE). Ephemeral datastore operations are mediated by high-throughput Redis instances with automated, atomic single-delivery guarantees enforced by custom Lua scripts that eradicate race conditions during read operations. Furthermore, the architecture complies with strict audit invariants (AUD-6), ensuring that payload identifiers are entirely excluded from uniform resource locator paths and query parameters, eliminating transit leakage across intermediary proxies and web server logs. Internal microservice communications, including PostgreSQL audit storage and Redis cache transactions, are hardened through automated Transport Layer Security (TLS) certificate authority provisioning. Continuous integration workflows automate security audits, end-to-end integration tests, and ephemeral preview deployments on dedicated subdomains via Tailscale HTTPS.

\unnumberedsection{INTRODUCTION}

In contemporary distributed computing environments, modern software engineering workflows demand frequent exchange of highly sensitive digital assets. Software developers, system operators, devops specialists, and cloud architects constantly transmit database credentials, private cryptographic keys, temporary infrastructure access tokens, and confidential application parameters. Despite the widespread adoption of secure transport protocols, the mechanisms employed for ad-hoc credential transmission remain predominantly insecure. Practical industry surveys reveal that sensitive credentials are routinely dispatched via corporate chat platforms, email threads, issue management trackers, and customer relationship management ticketing systems. 

These persistent communication channels fundamentally violate the principle of least privilege and data minimization. Messages stored within email repositories and enterprise messaging backends persist indefinitely, multiplying the attack surface across distributed cloud backups, employee workstations, and third-party SaaS infrastructure. A compromise of any singular administrative account or audit log repository frequently exposes a historical archive of active system credentials. Consequently, ephemeral secret-sharing systems—frequently designated as ``burn-after-reading'' services—have emerged as an essential defensive countermeasure. By enforcing strict temporal time-to-live restrictions and guaranteeing immediate destruction upon first consumption, ephemeral sharing restricts the exposure window of confidential tokens to the bare minimum duration required for operational handoff.

Nevertheless, an analysis of mainstream commercial and open-source ephemeral sharing utilities reveals substantial architectural vulnerabilities. Conventional implementations rely upon centralized server-side trust models. In such architectures, plaintext credentials are submitted directly to a remote server, which undertakes the responsibility of encrypting and storing the payload. In this scenario, the hosting infrastructure retains total visibility over the plaintext content, rendering the system vulnerable to memory scraping, database exfiltration, insider threats, and subpoena interception. Even among platforms claiming client-side encryption, grave architectural omissions persist: secret identifiers are routinely encoded directly within uniform resource locator (URL) paths or query strings. Because web proxies, load balancers, content delivery networks, and browser histories systematically record full HTTP request lines, secret identifiers are permanently leaked into infrastructure access logs. An adversary with passive read access to proxy logs can readily replay unconsumed identifiers, thereby intercepting sensitive credentials before the legitimate recipient accesses them.

The core motivation of this software engineering internship project is the development and rigorous implementation of \textbf{SecretShare}, an open-source, resilient, end-to-end encrypted secret-sharing ecosystem founded upon a strict zero-trust, zero-knowledge threat model. The primary objective is the realization of an application architecture wherein the centralized application server acts as a blind, untrusted storage broker. Under this architectural paradigm, cryptographic operations occur exclusively within client user agents utilizing the standardized W3C Web Crypto API. Cryptographic payloads are addressed to authenticated organizational identities, preventing unauthorized consumption even in the event of total transport-layer interception.

To accomplish this objective, the project fulfills the following engineering tasks:
\begin{itemize}
  \item design of an asynchronous microservice backend utilizing FastAPI, implementing strict body-based parameter verification to completely prevent credential leakage in HTTP request lines;
  \item implementation of a browser-based hybrid encryption engine combining asymmetric RSA-OAEP 2048-bit key wrapping with symmetric AES-256-GCM authenticated payload encryption;
  \item integration of an enterprise identity provider (Keycloak) supporting OpenID Connect and OAuth2 with Proof Key for Code Exchange to authenticate recipient devices and authorize secret access;
  \item engineering of an atomic, single-delivery destruction engine executing inside an in-memory Redis instance via Lua scripting to prevent race conditions during concurrent access;
  \item establishment of automated mutual TLS datastore encryption and turnkey container orchestration via Docker Compose and Traefik edge routing;
  \item development of an automated continuous integration and continuous deployment pipeline providing ephemeral pull-request previews with valid HTTPS subdomains via Tailscale.
\end{itemize}

The structure of this report is organized systematically into three principal chapters, followed by general conclusions and technical appendices. Chapter 1 provides a comprehensive domain analysis, evaluating the threat landscape, target audience, technical problem formulation, and comparative market alternatives. Chapter 2 details the architectural specification and system design, encompassing functional and non-functional requirements, edge routing topology, behavioral sequence modeling, and mathematical cryptographic specifications. Chapter 3 examines the practical implementation and empirical verification of the frontend, backend, ephemeral storage engine, automated test suites, and continuous deployment workflows.

\section{Domain Analysis}

The development of secure ephemeral sharing software requires a rigorous exploration of cryptographic principles, contemporary web architectures, operational threat models, and real-world administrative user behaviors. This chapter presents an in-depth investigation into the operational challenges of sensitive data exchange, establishes the threat model under which the system operates, identifies key stakeholder personas, defines the core value proposition of the proposed platform, and conducts an extensive comparative study of existing industry alternatives.

\subsection{Problem Overview and Security Threat Landscape}

In modern software development and DevOps practices, credential exchange is an inevitable daily operational requirement. During onboarding procedures, emergency incident remediations, database migrations, and manual configuration overrides, engineers are compelled to transmit high-value confidential data. This confidential data includes database connection strings, root private keys, cloud service account credentials, and third-party webhook signing secrets. Historically, these data items have been conveyed through general-purpose corporate communication software such as Slack, Microsoft Teams, Discord, Jira tickets, and corporate email systems.

The systemic danger of utilizing persistent communication channels lies in the durability and proliferation of the transmitted data. Typical enterprise chat platforms and email servers maintain continuous database backups and unencrypted internal logs. Once a credential is typed into a messaging channel, it is distributed across multiple message caching layers, mobile device notifications, and search indexing engines. The credential remains discoverable indefinitely. Statistical evaluations of corporate security incidents indicate that a substantial percentage of lateral network compromises originate from compromised read-only access to historical Slack or Jira workspaces, where stale passwords, access tokens, and administrative credentials remain unprotected.

Furthermore, traditional web applications that attempt to solve this challenge through ``one-time link'' services introduce severe architectural design flaws. The most prominent flaws identified in existing solutions include:
\begin{itemize}
  \item centralized server-side trust: the remote server generates and holds decryption keys, creating an attractive single point of compromise for malicious actors or untrusted server administrators;
  \item unauthenticated secret retrieval: links can be opened by anyone possessing the URL, meaning that accidental misrouting, clipboard theft, or shoulder surfing leads to immediate credential compromise;
  \item request-line identifier leakage: secret identifiers are placed in URL paths (such as \texttt{/secret/7a8f9b...}) or query parameters, causing automated logging by edge reverse proxies, corporate web filters, and browser navigation histories;
  \item destructive race conditions: simultaneous retrieval requests by automated link-crawlers (such as enterprise antivirus crawlers or chat link-unfurl bots) trigger premature secret deletion before the intended human recipient accesses the data.
\end{itemize}

To establish a resilient countermeasure, an application must enforce an absolute zero-knowledge paradigm. The storage backend must remain entirely blind to the contents of the secret, the encryption keys must never touch the server filesystem or memory space, and the secret identifier must be shielded from transparent transport-layer access logs.

\subsection{Target Audience and Stakeholder Analysis}

The operational scope of the SecretShare platform encompasses multiple professional profiles within organizational engineering and administrative ecosystems. Understanding the workflow requirements and risk tolerance of each stakeholder group is essential for establishing viable system ergonomics without degrading cryptographic security.

\textbf{1. DevOps and Site Reliability Engineering Teams.} Site reliability engineers routinely provision cloud infrastructure, rotate database credentials, and manage TLS certificates. Their primary requirement is an ultra-fast, scriptable, and turnkey mechanism to dispatch temporary infrastructure credentials to developers without manual GPG key exchange overhead. For these users, automated expiration, strict payload limits, and command-line compatibility represent high-priority operational requirements.

\textbf{2. Software Development Teams.} Distributed engineering teams require cross-platform credential handoffs across diverse operating environments (Linux, macOS, Windows). Developers require frictionless authentication via central enterprise accounts (single sign-on) and intuitive web user interfaces that prevent accidental key mismanagement. The platform must operate seamlessly within standard web browsers without requiring local software installations or custom cryptographic plugin configurations.

\textbf{3. Corporate Information Security and Audit Teams.} Security officers and compliance auditors are tasked with enforcing regulatory standards (e.g., SOC 2, ISO/IEC 27001, GDPR). Their primary operational requirement is the elimination of credential persistence in collaborative software and the enforcement of immutable audit logging. Auditors require clear traceability regarding who created a secret, who retrieved it, the precise timestamp of retrieval, and the verified cryptographic proof that the secret payload was immediately purged from memory upon consumption.

\textbf{4. External Contractors and Support Personnel.} Organizations frequently interface with external vendors and temporary contractors who do not possess corporate Active Directory or Google Workspace accounts. The platform must accommodate structured authorization flows while guaranteeing that credentials provisioned to external contractors expire automatically if not claimed within tight operational windows.

\subsection{Solution Concept and Core Value Proposition}

To address the documented threat landscape and satisfy stakeholder requirements, \textbf{SecretShare} is architected as an end-to-end encrypted, zero-trust ephemeral secret delivery platform. The fundamental premise of the solution is that the central server is treated as a potentially compromised, untrusted entity. All confidentiality guarantees are enforced at the network edge inside user web clients.

The conceptual architecture of the solution is founded upon four core engineering pillars:
\begin{itemize}
  \item client-side hybrid asymmetric/symmetric cryptography: the platform implements the W3C Web Crypto API directly within the browser document object model. Secrets are encrypted using symmetric AES-256-GCM under an ephemeral random key, which is subsequently encapsulated using asymmetric RSA-OAEP for the verified public keys of the recipient registered devices;
  \item zero-knowledge server blindness: the backend API accepts and persists only opaque ciphertext envelopes. The server possesses no mathematical capability to decrypt, inspect, or tamper with the payload;
  \item atomic single-delivery enforcement: secret destruction is executed within Redis using an atomic Lua script that simultaneously validates caller identity and executes instantaneous memory deletion, preventing duplicate reads and race-condition vulnerabilities;
  \item access log leak avoidance (Rule AUD-6): in strict adherence to audit rule AUD-6, secret payload identifiers are prohibited from appearing in HTTP URL paths or query strings during backend communication, eliminating request-line exposure across server access logs and proxy caches.
\end{itemize}

\subsection{Market Research and Comparative Analysis}

To substantiate the architectural innovation of SecretShare, an exhaustive comparative evaluation of contemporary credential sharing tools was performed. The evaluation benchmarks SecretShare against five leading commercial and open-source platforms: HashiCorp Vault, Bitwarden Send, One-Time Secret, Privnote, and Yopass.

\textbf{HashiCorp Vault} is an industry-standard secrets management platform designed for machine-to-machine identity and dynamic credential leasing. While Vault provides unmatched enterprise access control and encryption-at-rest capabilities, it is not optimized for ad-hoc, human-to-human secret sharing. Vault requires complex client configurations, specialized access permissions, and significant infrastructural overhead, rendering it impractical for rapid ad-hoc credential handoffs to external stakeholders.

\textbf{Bitwarden Send} provides end-to-end encrypted text and file transmission integrated within the Bitwarden password management suite. Bitwarden Send leverages client-side encryption and supports password-protected retrieval. However, it requires an active Bitwarden subscription for full administrative control and does not support native integration with external self-hosted OpenID Connect identity providers for decentralized organizational access.

\textbf{One-Time Secret and Privnote} represent widely utilized public web services offering burn-on-read links. Both platforms exhibit severe cryptographic deficiencies. Privnote performs all encryption server-side by default, exposing unencrypted credentials directly to the hosting provider. While One-Time Secret supports basic client-side passphrase protection, both services encode the secret identifier directly within the URL path. Consequently, links pasted into enterprise chat software or traversed across corporate proxy gateways are systematically inspected by automated web crawlers, frequently burning the secret before the recipient opens the link or leaking the identifier into access logs.

\textbf{Yopass} is an open-source tool developed by Johan Haals that utilizes client-side encryption via OpenPGP or subtle crypto primitives, with temporary storage in Memcached or Redis. While Yopass provides client-side encryption and ephemeral storage, it lacks native enterprise identity integration: anyone possessing the decryption key fragment can decrypt the payload. Furthermore, Yopass does not support multiple recipient devices, multi-device key registries, or atomic recipient identity verification prior to secret consumption.

\section{System Design and Architecture}

Engineering a resilient, zero-knowledge software architecture necessitates strict separation of concerns, defensive networking boundaries, and mathematically sound cryptographic protocol design. This chapter defines the technical requirement specifications of SecretShare, details the multi-container ingress and service topology, constructs formal Unified Modeling Language (UML) behavioral models, and specifies the underlying cryptographic engineering principles.

\subsection{Technical Requirements Specification}

The system requirements are derived from the operational threat model and the necessity of preventing plaintext compromise under any failure mode. The specifications are categorized into functional requirements governing system behavior and non-functional requirements establishing security, reliability, and performance boundaries.

\textbf{Functional Requirements (FR):}
\begin{itemize}
  \item \textbf{FR-01: Cryptographic Device Onboarding.} The system shall automatically generate a unique 2048-bit RSA-OAEP key pair within the authenticated user browser document object model upon initial login, persist the private key securely in local client-side storage (IndexedDB), and register the public key in Subject Public Key Info (SPKI) PEM format with the backend key registry.
  \item \textbf{FR-02: Recipient Public Key Retrieval.} The system shall provide an endpoint enabling any user agent to query the active device public keys associated with a designated recipient username prior to encryption.
  \item \textbf{FR-03: Client-Side Hybrid Encryption.} The web client shall generate an ephemeral 256-bit symmetric AES key, encrypt the plaintext payload using AES-256-GCM, wrap the AES key independently for each registered device key of the recipient using RSA-OAEP, and transmit the consolidated envelope to the backend.
  \item \textbf{FR-04: Non-Destructive Existence Check.} The system shall provide an unauthenticated endpoint accepting a secret identifier within the HTTP request body to verify the existence and validity of a secret without triggering its destruction.
  \item \textbf{FR-05: Authenticated Atomic Reveal.} The system shall provide a secure retrieval endpoint that authenticates the caller via Bearer token, verifies that the caller matches the recipient identity encapsulated in the envelope, atomically purges the envelope from storage, and returns the encrypted ciphertext payload.
  \item \textbf{FR-06: Burn-After-Reading Warning Notice.} The user interface shall intercept secret links and manual retrieval inputs, conduct an existence pre-check, and render an explicit confirmation modal warning the user that retrieval will permanently destroy the secret from the server before executing the reveal operation.
\end{itemize}

\textbf{Non-Functional Requirements (NFR):}
\begin{itemize}
  \item \textbf{NFR-01: Zero-Knowledge Blindness.} The backend server and persistent storage engines shall possess no algorithmic mechanism to decrypt stored ciphertext. No plaintext secret data or raw symmetric encryption keys shall ever be received, processed, or logged by the server.
  \item \textbf{NFR-02: Audit Invariant AUD-6 (No URL Identifiers).} The application shall strictly prohibit secret payload identifiers from appearing in HTTP URL paths or query strings across all backend API endpoints. Payload identifiers must be transmitted exclusively within JSON request bodies or client-side URL hash fragments.
  \item \textbf{NFR-03: Single Delivery Guarantee.} The storage layer must guarantee strict single-delivery semantics. Concurrent requests targeting the same secret identifier must never both receive the secret payload.
  \item \textbf{NFR-04: Maximum Payload Constraints.} The system shall enforce a strict payload boundary of 64 kilobytes (65,536 UTF-8 bytes) per secret envelope to prevent denial-of-service memory exhaustion on the Redis storage engine.
  \item \textbf{NFR-05: Transport and Datastore Encryption.} All external network traffic must be encrypted via TLS 1.3/1.2 at the reverse proxy boundary. All internal network traffic between application microservices, the PostgreSQL database, and the Redis cache must be encrypted via automated internal TLS with mutual certificate authority validation.
\end{itemize}

\subsection{Behavioral Modeling and Protocol Workflows}

The operational behavior of SecretShare is formalized through discrete interaction protocols governing key onboarding, secret transmission, and secret retrieval.

\textbf{1. Device Key Registration Workflow.} Before an authenticated user can receive encrypted secrets, their client user agent must register an active cryptographic identity.
According to Figure 2.2, upon successful authentication through Keycloak, the Next.js frontend invokes the Web Crypto API to generate an asymmetric RSA-OAEP key pair. The private key is serialized and committed to the browser persistent IndexedDB storage engine. The public key is exported into SPKI format, encoded as PEM text, and dispatched via registration endpoint accompanied by the user Bearer JWT. The FastAPI backend validates the token, extracts the username, and records the device public key in the PostgreSQL table.

\imageplaceholder{sequence-key-registration}{UML sequence diagram illustrating browser RSA-OAEP key generation, IndexedDB persistence, and SPKI public key registration via FastAPI and PostgreSQL}{Device Public Key Registration Protocol}{sequence_key_registration.png}

\textbf{2. Secret Creation and Hybrid Encryption Protocol.} The sender workflow operates completely client-side up to the moment of final envelope dispatch.
According to Figure 2.3, the sender specifies the recipient username and the plaintext secret within the web interface. The frontend queries the recipient device keys. The browser generates a cryptographically secure 256-bit symmetric key ($K_{AES}$) and a 96-bit initialization vector ($IV$). The plaintext is encrypted under AES-256-GCM. Subsequently, $K_{AES}$ is encrypted independently for each recipient device public key using RSA-OAEP. The resulting envelope:
\begin{equation}
\mathcal{E} = \{ \text{recipient\_id}, [\{ \text{device\_id}, E_{RSA}(K_{AES}) \}, \dots], IV, C, \text{ttl\_seconds} \}
\label{eq:envelope}
\end{equation}
is transmitted to the backend. In formula (2.1), $\text{recipient\_id}$ represents the target Keycloak username, $E_{RSA}$ denotes the asymmetric key wrapping operation, $IV$ is the 96-bit initialization vector, $C$ represents the ciphertext, and $\text{ttl\_seconds}$ defines the temporal lifetime of the secret. The backend generates a 256-bit cryptographically random token identifier ($ID$), persists $\mathcal{E}$ in Redis under key \texttt{s:\{ID\}} with the designated TTL, and returns the identifier to the sender.

\imageplaceholder{sequence-secret-creation}{UML sequence diagram depicting recipient key retrieval, browser-side AES-GCM encryption, RSA-OAEP key encapsulation, and envelope storage in Redis}{Hybrid Encryption and Secret Creation Protocol}{sequence_secret_creation.png}

\textbf{3. Secret Retrieval, Existence Verification, and Atomic Burn.} To prevent unauthorized consumption and accidental link expiration, retrieval is executed as a two-phase protocol.
According to Figure 2.4, when a recipient accesses a secret link (\texttt{/?id=\{ID\}}), the frontend immediately executes an existence verification by sending an existence check request with the identifier in the request body. If the secret exists, the application displays the Burn-After-Reading Warning Notice modal. If the user is unauthenticated, the modal prompts an OIDC login sequence that redirects back to the secret link upon completion.

When the recipient confirms the reveal operation by clicking ``Reveal \& Burn'', the browser executes the reveal request with the payload identifier and their Bearer authentication token. The FastAPI backend validates the token and invokes the atomic Redis Lua script. The Lua script verifies that the authenticated user matches the recipient identifier stored within the envelope. If matched, the script executes an atomic deletion command and returns the envelope. If identity verification fails, the secret is preserved in storage, and HTTP 403 Forbidden is returned. Upon receiving the envelope, the recipient browser retrieves their private RSA key from IndexedDB, unwraps the symmetric $K_{AES}$, decrypts the ciphertext $C$, and presents the plaintext in memory.

\imageplaceholder{sequence-secret-reveal}{UML sequence diagram showing existence check, warning modal, atomic Lua burn in Redis, and client-side RSA/AES decryption}{Atomic Reveal, Identity Verification, and Decryption Protocol}{sequence_secret_reveal.png}

\subsection{Cryptographic Engineering and Zero-Knowledge Model}

The cryptographic architecture of SecretShare is engineered to provide forward secrecy, integrity protection, and resilience against chosen-ciphertext attacks.

\textbf{1. Symmetric Cryptography (AES-256-GCM).} Plaintext encryption utilizes Advanced Encryption Standard in Galois/Counter Mode (AES-GCM) with a 256-bit key length ($|K_{AES}| = 256 \text{ bits}$) and a 96-bit initialization vector ($|IV| = 12 \text{ bytes}$). AES-GCM provides authenticated encryption with associated data (AEAD), ensuring both confidentiality and cryptographic integrity. Any unauthorized modification of the ciphertext or IV during storage or transit triggers an authentication tag verification failure, causing the decryption operation to abort before returning corrupted data.

\textbf{2. Asymmetric Key Encapsulation (RSA-OAEP).} Public key encapsulation is performed using RSA with Optimal Asymmetric Encryption Padding (RSA-OAEP) configured with a 2048-bit modulus and a SHA-256 hash digest function. OAEP incorporates randomized padding to ensure probabilistic encryption, defeating replay and algebraic homomorphism attacks. The encapsulation operation for device $j$ with public key $PK_j$ is defined by:
\begin{equation}
C_{key, j} = \text{RSA-OAEP-ENCRYPT}(PK_j, K_{AES}, \text{SHA-256})
\label{eq:rsa_oaep}
\end{equation}
In formula (2.2), $PK_j$ denotes the RSA public key of device $j$, $K_{AES}$ represents the symmetric AES content encryption key, and SHA-256 represents the cryptographic hash function utilized for mask generation.

\textbf{3. Atomic Redis Single-Delivery Script.} A critical innovation of SecretShare is the resolution of the ``decrypt-then-burn'' race condition. In classical ephemeral systems, an application reads a secret, inspects authorization, and then deletes it. If two concurrent requests arrive simultaneously, both read the secret before either deletes it, violating single-delivery invariants. Conversely, executing an atomic delete-on-read deletes the secret even if the caller was unauthorized, causing denial of service to the legitimate recipient.

To resolve this vulnerability, SecretShare implements an atomic Redis Lua script evaluated directly on the Redis engine thread:
\begin{lstlisting}[language=SQL]
-- Atomic Recipient-Checked Burn Script (Redis Lua)
local payload = redis.call('GET', KEYS[1])
if not payload then 
    return {'missing'} 
end
local ok, envelope = pcall(cjson.decode, payload)
if not ok or type(envelope) ~= 'table' or envelope['recipient_id'] ~= ARGV[1] then
    return {'denied'}
end
redis.call('DEL', KEYS[1])
return {'burned', payload}
\end{lstlisting}

Because Redis processes Lua scripts as a singular atomic transaction, the state verification and deletion are indivisible. An unauthorized caller receives a denied status while the secret remains intact for the genuine recipient. When the genuine recipient invokes the script, the envelope is atomically returned and deleted simultaneously.

\textbf{4. Security Audit Invariant AUD-6.} To prevent transport-layer access log leakage, SecretShare enforces invariant AUD-6. Web servers (e.g., Uvicorn, Nginx, Apache), reverse proxies (Traefik), and browser history engines systematically record HTTP request lines:
\begin{equation}
\text{Request-Line} = \text{Method} \quad \text{Request-URI} \quad \text{HTTP-Version}
\label{eq:request_line}
\end{equation}
In formula (2.3), $\text{Method}$ denotes the HTTP action, $\text{Request-URI}$ defines the target path and query parameters, and $\text{HTTP-Version}$ designates the protocol version.

If a secret identifier is placed in the URI, the full 256-bit identifier is permanently recorded in access logs across every intermediary network hop. Under rule AUD-6, all endpoints accepting a payload identifier require it strictly within the serialized JSON request body:
\begin{lstlisting}[language=SQL]
POST /api/secrets/reveal HTTP/1.1
Host: pr-30.tailnet.ts.net
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{"payload_id": "v7x9Bq2L1mZ0k8wRtN5yP4uA3cE6dF8gH1jK2lM3nO4"}
\end{lstlisting}
The request URI recorded in access logs is exclusively \texttt{/api/secrets/reveal}, completely shielding the sensitive payload identifier from infrastructure logging.

\section{Implementation and System Verification}

The practical engineering of SecretShare emphasizes modern asynchronous programming patterns, strict type safety, zero external cryptographic runtime dependencies on the client, and fully automated verification pipelines. This chapter documents the implementation details of the frontend client, backend application, database persistence layer, and the continuous integration and preview deployment infrastructure.

\subsection{Frontend Web Client Implementation}

The user interface of SecretShare is developed utilizing Next.js (App Router) and TypeScript. The application is deliberately architected with minimal external UI dependencies to maintain a lightweight footprint, high rendering performance, and a minimized attack surface.

\textbf{1. Browser Cryptographic Engine (\texttt{web/lib/crypto.ts}).} Cryptographic operations interface directly with the W3C Web Crypto API (\texttt{window.crypto.subtle}). Key generation is executed during user onboarding:
\begin{lstlisting}[language=Python]
export async function generateRsaKeyPair(): Promise<CryptoKeyPair> {
  return await window.crypto.subtle.generateKey(
    {
      name: 'RSA-OAEP',
      modulusLength: 2048,
      publicExponent: new Uint8Array([1, 0, 1]),
      hash: 'SHA-256',
    },
    true,
    ['encrypt', 'decrypt']
  )
}
\end{lstlisting}
Public keys are exported into binary SPKI format, base64-encoded, and formatted with standard PEM header boundaries before network transmission. Symmetric encryption generates a 256-bit cryptographic AES key using \texttt{crypto.getRandomValues()} and returns base64-encoded ciphertext and initialization vectors.

\textbf{2. Local Keystore Persistence (\texttt{web/lib/key-store.ts}).} The generated RSA private key must persist across browser sessions without leaving the client device. The application implements an asynchronous storage abstraction over the browser IndexedDB API (\texttt{secretshare\_keystore}). Keys are indexed by the authenticated Keycloak username, guaranteeing cryptographic isolation between distinct user sessions on the same physical workstation.

\textbf{3. User Interface and Burn Warning Modal (\texttt{web/app/page.tsx}).} The user interface is structured into two primary operational regions: secret creation and secret retrieval.
According to Figure 3.1, when a user accesses a shareable link or pastes a payload identifier into the retrieval field, the application initiates an existence check. Upon positive confirmation, the application renders a prominent modal dialog displaying the \textbf{Burn-After-Reading Warning}. The dialog informs the recipient that proceeding with the reveal operation will irrevocably destroy the secret from server storage. If the visitor is unauthenticated, the modal dynamically renders an authentication button linking to the Keycloak OIDC login sequence, returning the user to the pending reveal state upon successful credential verification.

\subsection{Backend Microservice and Ephemeral Storage Engine}

The backend application is implemented using FastAPI, Python 3.11, and modern asynchronous concurrency primitives (\texttt{asyncio}).

\textbf{1. Centralized Configuration Management (\texttt{api/app/core/config.py}).} Configuration management is centralized using Pydantic Settings (\texttt{pydantic-settings}). Application configuration parameters—including database connection URIs, Redis connection credentials, Keycloak client settings, payload limits, and Time-to-Live bounds—are loaded from environment variables and strictly validated at container startup. Direct calls to \texttt{os.getenv} within operational service code are strictly prohibited, preventing runtime type coercion errors.

\textbf{2. Relational Schema and Database Migrations.} Relational persistence is governed by SQLAlchemy ORM and Alembic. The database schema encompasses three core tables:
\begin{itemize}
  \item \texttt{users}: maintains unique internal user identifiers, Keycloak identity mappings, username references, and creation timestamps;
  \item \texttt{device\_keys}: stores device public keys (SPKI PEM), hardware platform identifiers, descriptive labels, and registration timestamps linked via foreign key to \texttt{users};
  \item \texttt{audit\_events}: records security audit events, including secret creation, existence checks, reveal attempts, and access denial events.
\end{itemize}

In strict compliance with audit invariant AUD-6, the \texttt{audit\_events} table enforces a database-level check constraint ensuring that only the first 8 characters of a payload identifier are stored as an audit reference prefix. Full payload identifiers, plaintext secrets, and decryption keys are permanently excluded from database persistence. Database migrations execute automatically during container entrypoint execution, guaranteeing schema synchronization prior to application traffic ingestion.

\textbf{3. Defensive Security Middlewares.} The FastAPI application is shielded by multiple custom ASGI middleware layers:
\begin{itemize}
  \item \textbf{BodySizeLimitMiddleware:} inspects incoming HTTP \texttt{Content-Length} headers and active stream byte counts, immediately aborting requests exceeding 64 KB with HTTP 413 Payload Too Large before memory buffer allocation;
  \item \textbf{TrustedProxyMiddleware:} parses \texttt{X-Forwarded-For} headers exclusively from trusted proxy CIDR ranges (Traefik and Tailscale interfaces), extracting the authentic remote client IP address for accurate rate limiting and security auditing;
  \item \textbf{Input Masking Error Handlers:} global exception handlers intercept validation errors and strip the original request input from the JSON error response, ensuring that malformed payloads are never reflected in server error bodies.
\end{itemize}

\unnumberedsection{CONCLUSIONS}

The software engineering internship project successfully designed, implemented, and verified \textbf{SecretShare}, an enterprise-ready, zero-trust ephemeral secret delivery platform. By addressing the fundamental security vulnerabilities inherent in traditional secret-sharing utilities, the project establishes a robust reference architecture for secure, temporary credential handoffs.

The principal technical achievements realized throughout the internship project include:
\begin{itemize}
  \item the successful realization of a zero-knowledge threat model, ensuring that the central application backend acts solely as a blind ciphertext storage broker with zero visibility into plaintext secrets or decryption keys;
  \item the implementation of a robust browser-based hybrid encryption engine combining asymmetric RSA-OAEP 2048-bit key wrapping with symmetric AES-256-GCM authenticated encryption utilizing native W3C Web Crypto primitives;
  \item the eradication of destructive race conditions and link-crawler vulnerabilities through the design of an atomic Redis Lua single-delivery script;
  \item the rigorous enforcement of security audit rule AUD-6 across all API routes, preventing secret identifier leakage into reverse proxy logs, corporate firewalls, and browser histories;
  \item the implementation of turnkey datastore security, establishing automated internal TLS certificate authority provisioning across PostgreSQL and Redis datastores;
  \item the construction of an automated continuous integration and ephemeral preview deployment workflow utilizing Tailscale HTTPS subdomains, accelerating collaborative verification.
\end{itemize}

Despite these substantial achievements, certain operational and architectural limitations remain identified for future iterations:
\begin{itemize}
  \item \textbf{Device-Specific Decryption Guard:} currently, if a recipient opens a secret on a browser whose device key was not included during encryption (e.g., a newly installed browser), the secret is burned upon retrieval and decryption fails locally. A future enhancement should require the client to supply its registered device identifier during reveal, allowing the server to refuse the request without burning if no matching key exists;
  \item \textbf{Non-Extractable CryptoKey Objects:} while private keys are currently isolated within client IndexedDB storage, generating them as non-extractable CryptoKey handles will provide hardened resilience against potential cross-site scripting (XSS) extraction;
  \item \textbf{User Public Key Enumeration Protection:} the public key retrieval endpoint currently returns HTTP 404 when a user does not exist, permitting username enumeration. Requiring authentication or returning a uniform response structure will eliminate this exposure vector;
  \item \textbf{Sender Management Dashboard:} future milestones will implement an authenticated sender interface allowing users to view the status of active outgoing secrets, monitor retrieval audit logs, and trigger early revocations prior to automatic TTL expiration.
\end{itemize}

In conclusion, SecretShare proves that uncompromising cryptographic security, zero-trust server blindness, and frictionless user ergonomics can be successfully harmonized within modern web application architectures.

// Web Crypto Hybrid Encryption Implementation (web/lib/crypto.ts)
export async function createEncryptedEnvelope(
  plaintext: string,
  recipientDevices: DeviceKeyItem[]
): Promise<{ iv: string; ciphertext: string; encryptedKeys: any[] }> {
  // 1. Generate an ephemeral random 256-bit AES key
  const aesKey = await window.crypto.subtle.generateKey(
    { name: 'AES-GCM', length: 256 },
    true,
    ['encrypt']
  );

  // 2. Encrypt plaintext payload with AES-256-GCM
  const iv = window.crypto.getRandomValues(new Uint8Array(12));
  const encodedPlaintext = new TextEncoder().encode(plaintext);
  const ciphertextBuffer = await window.crypto.subtle.encrypt(
    { name: 'AES-GCM', iv },
    aesKey,
    encodedPlaintext
  );

  // 3. Export raw AES key bytes for asymmetric encapsulation
  const rawAesKey = await window.crypto.subtle.exportKey('raw', aesKey);

  // 4. Wrap AES key for each recipient device using RSA-OAEP
  const encryptedKeys = await Promise.all(
    recipientDevices.map(async (device) => {
      const rsaPublicKey = await importPublicKeyFromSpkiPem(device.public_key);
      const wrappedKeyBuffer = await window.crypto.subtle.encrypt(
        { name: 'RSA-OAEP' },
        rsaPublicKey,
        rawAesKey
      );
      return {
        device_id: device.device_id,
        platform: device.platform,
        encrypted_aes_key: bufferToBase64(wrappedKeyBuffer),
      };
    })
  );

  return {
    iv: bufferToBase64(iv),
    ciphertext: bufferToBase64(ciphertextBuffer),
    encryptedKeys,
  };
}
