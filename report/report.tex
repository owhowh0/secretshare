\plainheading{Abstract}

This report presents SecretShare, a web application for sending a confidential value, such as a database password or an API key, to one named colleague so that the value can be read exactly once and is then destroyed. The problem addressed is that credentials exchanged in chat, e-mail and issue trackers remain stored in those systems indefinitely, while existing one-time-link services either encrypt on the server or let anyone who obtains the link read the secret.

The proposed solution encrypts every secret in the sender's browser with AES-256-GCM and wraps the content key with RSA-OAEP for the devices that the recipient has registered. The server stores only the resulting envelope in Redis with a time to live and never receives the plaintext or an unwrapped key. Retrieval requires the recipient to sign in through Keycloak with OpenID Connect and PKCE, and a Lua script executed inside Redis checks the caller and deletes the envelope in one atomic step, so a wrong recipient cannot destroy the secret and two readers cannot both obtain it. Secret identifiers are sent only in request bodies, which keeps them out of the request lines recorded by proxies and web servers.

The minimum viable product was built by a team of five students during a four-week internship with a FastAPI back end, a Next.js front end, PostgreSQL for device keys and an append-only audit log, and Traefik for routing. Methods included threat analysis, UML modelling, test-driven fixes of discovered vulnerabilities and continuous integration with a preview environment for every pull request. The latest pipeline run executed 176 automated API and security tests, 18 internal-TLS tests and 5 live OAuth integration tests without failures. The report also records the limitations that remain, including multi-factor authentication, a restricted database role for the audit log and protection against losing a secret on an unregistered device, as the plan for the continuation of the project in the PBL course.

\vspace{0.6cm}
\noindent
\textbf{Keywords:} ephemeral secret sharing, end-to-end encryption, hybrid cryptography, zero-knowledge storage, OpenID Connect, Redis, secure software development.

\unnumberedsection{INTRODUCTION}

Software teams exchange credentials every day: a developer needs a database password during onboarding, an operator shares a temporary cloud token during an incident, and a contractor receives an API key for an integration. In practice these values are usually pasted into the tools the team already uses. The GitGuardian report on secrets sprawl found leaked secrets in 2.4\% of the corporate Slack channels and 6.1\% of the Jira tickets that it analysed \cite{gitguardian2025}. Such messages are kept for years, copied into backups and indexed for search, so one compromised account exposes a history of credentials. Stolen credentials matter because credential abuse remained the most common initial access vector in the breaches analysed in the 2025 Verizon Data Breach Investigations Report \cite{verizon2025}.

One-time secret links were created to shorten this exposure: a secret is stored temporarily and deleted after the first read. However, the common designs leave three weaknesses. When encryption happens on the server, the operator of the service can read every secret. When the link itself is the only credential, anybody who sees the link, including a chat application that fetches it to build a preview, can consume the secret. When the identifier is part of the URL path or query, it is written into the access logs of every proxy and web server on the way. These weaknesses are analysed in detail in Chapter~1.

The project was carried out as part of the Development of Secure Applications (DAS) internship, whose brief asks teams to build a realistic minimum viable product in which security is designed in from the start: encryption of data in transit and at rest, OAuth~2.0 for API access, input validation, error handling that does not disclose information, and documentation of threats, risks and incident response \cite{dasbrief}. A one-time secret relay suits this brief well because every one of its functions is security-relevant, and because its correctness can be expressed as a small number of verifiable invariants.

The purpose of the project is to design and implement SecretShare, a relay in which the server can neither read a secret nor hand it to anyone except the named recipient, and to verify these properties with automated tests. To achieve this purpose, the following objectives were set:
\begin{itemize}
  \item to analyse the problem domain, the threat actors and the existing solutions;
  \item to specify functional and non-functional requirements, including measurable security invariants;
  \item to model the behaviour and the structure of the system in UML;
  \item to implement browser-side hybrid encryption, recipient authentication and atomic single delivery;
  \item to verify the security controls with automated tests and a continuous integration pipeline;
  \item to document the remaining limitations and a plan for the PBL semester.
\end{itemize}

For developers, operators and security staff the expected impact is that a shared credential lives for minutes in an encrypted store instead of years in a chat history.

The work was done by a team of five students during the September 2026 internship; the repository was created on 9 September. Changes went through pull requests on GitHub, and by the time of writing 28 pull requests had been merged, each of them tested automatically and, from the middle of the month, deployed to its own preview environment \cite{secretsharerepo}.

Chapter~1 of the report analyses the domain and the market, Chapter~2 presents the requirements, the UML models and the cryptographic design, and Chapter~3 describes the implementation, the security controls, the testing and the problems solved during the internship.

\section{Domain Analysis}

This chapter defines the problem that SecretShare addresses and the attackers that the design must withstand. It then describes the intended users and their needs, the concept of the solution and the scope chosen for the first version, and compares the concept with existing tools.

\subsec{Problem Overview}

A credential shared between people has two properties that make it dangerous: it grants access by itself, and it is usually valid for much longer than the conversation in which it was sent. General-purpose communication tools are built to preserve messages. A password typed into a chat is stored on the provider's servers, synchronised to every device of every participant, included in exports and backups, and indexed for search. Deleting the message later rarely removes all of these copies. The collaboration tools that engineering teams use most, such as Slack, Jira and Confluence, are therefore a recurring source of leaked secrets \cite{gitguardian2025}.

One-time secret services reduce the lifetime of the copy, but an analysis of their typical design shows four weaknesses that SecretShare is intended to remove.

The first weakness is trust in the server. If the plaintext is sent to the server and encrypted there, the confidentiality of every secret depends on the honesty and security of the operator, of the hosting provider and of every administrator with access to the machine. A single compromise of the server exposes every secret that passes through it while the attacker is present.

The second weakness is the link as the only credential. A link that is sufficient to read the secret can be used by anyone who sees it: a colleague who reads over the recipient's shoulder, a clipboard manager that stores history, or a mistaken paste into the wrong channel. The service cannot tell the intended recipient from any other holder of the link.

The third weakness concerns request lines. HTTP/1.1 sends the method and the request target, that is the path and the query string, in the first line of every request \cite{rfc9112}. Web servers and reverse proxies record this line in their access logs by default, and browsers store it in their history. A secret identifier placed in the path or the query therefore ends up in log files that live far longer than the secret itself, and anyone with read access to those logs can use an unconsumed identifier. Only the fragment part of a URL, after the \texttt{\#} sign, is processed by the client and not sent to the server \cite{rfc3986}.

The fourth weakness is automatic consumption. Chat applications fetch a pasted link to build a preview \cite{slackunfurl}, and security gateways scan links in incoming mail. If opening the link is enough to consume the secret, such an automated request destroys it before the person for whom it was intended opens it, or worse, a scanner that stores responses keeps a copy.

To reason about these weaknesses systematically, the team defined six threat actors, from a reader of log files to a compromised server.

\subsec{Target Audience}

SecretShare is intended for organisations in which people regularly hand credentials to each other and which already operate a central identity provider. The needs of the target users were derived from the team's experience, discussions with the mentor and the DAS brief \cite{dasbrief}; no formal survey was carried out, which is a gap to be closed in the PBL semester. Four groups of users were identified.

Developers form the largest group. They receive database passwords, API keys and test accounts when they join a project or start a new integration, and they send such values to colleagues who work on other parts of the system. Their main needs are speed and simplicity: a secret must be sent in less than a minute, from any operating system, without installing software or managing encryption keys by hand.

DevOps engineers and site reliability engineers provision infrastructure and rotate credentials. They often need to hand over a temporary token during an incident, under time pressure and in a channel that other people can see. For them it is essential that a secret expires automatically if it is not read, that its size is limited, and that the handover works through an interface that they can also call from scripts.

Security officers and auditors do not send secrets themselves, but they are responsible for policies that forbid credentials in chat. They need a sanctioned alternative that users will actually adopt, and evidence after the fact: who created a secret, whether and when it was read, and whether someone else tried to read it. At the same time the evidence must not become a new store of secrets.

External contractors and partners are the fourth group. They are often given accounts in the organisation's identity provider for the duration of a contract. The system must allow them to receive a secret addressed to their account, and must make sure that a secret sent to a contractor who never opens it disappears on its own. Anonymous recipients are not served, as that would reintroduce the link-holder weakness.

\subsec{Solution Concept}

SecretShare is a relay for secrets addressed to a named person. A signed-in sender types the secret and the user name of the recipient. The browser encrypts the secret for the devices that the recipient has registered, sends the encrypted envelope to the server and receives a share link. The recipient opens the link, sees a warning that the secret will be destroyed, signs in if necessary and confirms. The server hands the envelope to the recipient and deletes it in the same step, and the recipient's browser decrypts it locally. The concept rests on four principles.

The first principle is that the server is blind. Encryption and decryption use the Web Cryptography API of the browser \cite{webcrypto}, and the server receives only ciphertext, an initialisation vector and content keys wrapped with the recipients' public keys. The server judges the envelope only by its size and by the validity of its fields.

The second principle is that access is bound to identity, not to the link. Reading a secret requires a valid access token issued by the organisation's identity provider, and the server hands out the envelope only if the user in the token is the recipient chosen by the sender. The link merely identifies which secret to fetch.

The third principle is that a secret is delivered once. The check of the recipient and the deletion happen as one atomic operation inside the data store, so neither a wrong recipient nor two parallel requests of the right recipient can break the guarantee.

The fourth principle is that nothing secret is logged. Identifiers travel in request bodies, never in the path or query of an API request, error responses do not echo input, and the audit log stores only a short prefix of an identifier.

\leadin{As shown in Table~1.3, a secret passes through a small number of states, and every state has a defined location and a defined protection.}

A request by a user who is not the recipient, and an existence check made when the link is opened, leave the secret in the stored state. This distinction is what protects the secret from link previews and from a wrong recipient.

Following the DAS brief \cite{dasbrief}, the team implemented in September the measures without which the concept does not hold: browser-side encryption, OAuth~2.0 and OpenID Connect authentication, atomic delivery, identifiers kept out of logs, internal TLS, validation and rate limiting. Multi-factor authentication and a sender dashboard were planned for October to December.

\subsec{Market Research}

The concept was compared with four tools whose design is documented by their authors, so that the comparison relies on primary sources.

HashiCorp Vault is a secrets management system for machines and services. Its response wrapping feature places a secret behind a single-use token with a limited lifetime, which can be passed to another party \cite{vaultwrap}. The mechanism is strong, but it assumes that both parties use Vault, which is disproportionate for an occasional handover between two people.

Bitwarden Send is part of the Bitwarden password manager. Content is encrypted when a Send is created and decrypted when the recipient opens the link; a Send can be limited by the number of accesses, can carry an optional password, and has a lifetime of at most 31 days \cite{bitwardensend}. Recipients do not need an account, which is convenient but means that, without the optional password or e-mail verification, the link alone grants access.

Yopass is an open-source service that encrypts the secret in the browser with OpenPGP and places the decryption key in the URL fragment, so that the server never receives it; secrets can be deleted after the first retrieval \cite{yopass}. The open-source version has no user accounts, so the link is again the only credential, while OpenID Connect authentication is offered in a commercial edition.

Onetime Secret is a widely used public service whose secrets, according to its own description, are encrypted on its servers, optionally with a sender's passphrase, and deleted after one display \cite{onetimesecret}.

\subsec{Behavioural Modelling}

The behaviour of the system is modelled first by its use cases, which show who interacts with SecretShare and for what purpose.

\diagram{usecase}{Use case diagram of SecretShare}{fig:usecase}{According to Figure~2.1, the system has two human actors and two external actors.}

The sender signs in and creates secrets; creating a secret includes looking up the recipient's device keys. The recipient signs in, opens share links and reveals secrets; opening a link includes the existence check, and revealing includes the local decryption. Signing in includes the registration of the device key. Keycloak takes part in every sign-in, and the expiry mechanism of Redis acts as a timer that removes unread secrets.

The two central use cases are described in more detail by sequence diagrams.

\diagram{seq_create}{Sequence diagram of secret creation}{fig:seqcreate}{According to Figure~2.2, the creation of a secret starts with a request for the recipient's public keys.}

The browser then generates a fresh content key and initialisation vector, encrypts the plaintext and wraps the content key once for each device. The API checks the size of the request and the requested lifetime, generates an identifier, stores the envelope in Redis with the lifetime as its expiry, writes an audit event and returns the identifier together with the expiry time.

\diagram{seq_reveal}{Sequence diagram of secret retrieval}{fig:seqreveal}{According to Figure~2.3, the retrieval of a secret is divided into two phases.}

In the first phase the browser only asks whether the secret exists. This request is safe for link previews and for accidental clicks, because it never changes the state of the secret; its positive answer makes the interface show a warning that reading will destroy the secret. The second phase starts only when the person confirms. If the person is not signed in, the authorisation code flow is carried out first. The reveal request carries the identifier in the body and the access token in the header. The API verifies the token, takes the user name from it and runs the burn script, which returns one of three results: the envelope, a denial or a miss. The audit event and the HTTP status follow from this result, and on success the browser decrypts the secret locally.

The registration of a device key, which precedes both flows, is shown in Appendix~A. It is performed automatically after the first sign-in in a browser, so the user never handles keys directly.

\subsec{Structural Modelling}

The structure of the system is described by a component diagram, which shows the deployable parts, their internal modules and the interfaces between them.

\diagram{component}{Component diagram of SecretShare}{fig:component}{According to Figure~2.4, SecretShare consists of five runtime components behind a single edge router, plus a start-up component that prepares certificates; all of them run as containers started together by Docker Compose.}

Traefik is the only component exposed to the network \cite{traefik}. It routes requests by path prefix: \texttt{/api} goes to the FastAPI service, \texttt{/keycloak} to the identity provider and all other paths to the Next.js web application. Because every component is reached through the same origin, the browser's same-origin policy and the Content Security Policy can be as strict as \texttt{'self'}, and no cross-origin resource sharing is needed. In preview and staging environments Tailscale Serve terminates HTTPS in front of Traefik and gives each environment its own host name with a valid certificate \cite{tailscaleserve}. A secure context is not optional here: the Web Cryptography API is available only on HTTPS pages or on \texttt{localhost}.

The web component is a Next.js application \cite{nextjs} that serves the user interface and uses Auth.js to run the OpenID Connect sign-in with Keycloak \cite{authjs}. All cryptographic work runs in the user's browser, in the modules shown in the upper part of Figure~2.4.

The API component is a FastAPI application \cite{fastapi} organised in layers. Middleware limits the body size, determines the real client address behind trusted proxies and adds security headers. Route handlers validate input with Pydantic schemas and apply rate limits. Services implement the use cases, the \texttt{SecretStore} class wraps Redis and the Lua burn script, and the \texttt{AuditService} writes audit events. Authentication is a dependency that verifies access tokens against the signing keys that Keycloak publishes as a JSON Web Key Set.

Keycloak is the identity provider \cite{keycloak}. It holds the user accounts, performs authentication and issues signed JSON Web Tokens \cite{rfc7519} for the public client \texttt{secretshare-api}.

Redis holds the encrypted envelopes, each under the key \texttt{s:<payload\_id>} with an expiry equal to the lifetime of the secret. Redis is used only as volatile storage, so an unread secret disappears without any clean-up job.

PostgreSQL holds the data that must persist: the users known to the relay, their device public keys and the audit log. The data model is shown in Appendix~B. It contains three tables. The \texttt{users} table identifies a person by a platform and a platform-specific user name, which prepares the model for chat platforms. The \texttt{device\_keys} table stores public keys only, with a \texttt{revoked\_at} column that marks keys that are no longer active. The \texttt{audit\_events} table is append-only and is described in Chapter~3.

The \texttt{tls-init} component runs once at start-up. It creates a private certificate authority and issues server certificates for PostgreSQL and Redis. The API connects to both data stores over TLS and verifies their certificates against this authority; Redis listens only on its TLS port, with the plaintext port disabled. The TLS is not mutual: the data stores do not ask the API for a client certificate. PostgreSQL authenticates the API with a password, whereas Redis currently accepts any TLS client on the internal network without authentication, which is recorded as a limitation in Section~3.2.

\subsec{Cryptographic Design and Security Invariants}

The cryptographic scheme is a hybrid one: a symmetric cipher protects the secret and an asymmetric cipher protects the symmetric key for each of the recipient's devices. This combination allows a secret of any length up to the size limit to be encrypted once and addressed to several devices, while every device keeps its own private key.

For the content, the browser draws a 256-bit key $K$ and a 96-bit initialisation vector from its cryptographically secure random number generator and encrypts the plaintext with AES in Galois/Counter Mode \cite{nist80038d}. GCM is an authenticated mode: the ciphertext carries a 128-bit tag, and any change to the ciphertext or the initialisation vector makes decryption fail instead of producing altered plaintext. A new key and initialisation vector are used for every secret, which satisfies the requirement of GCM that an initialisation vector is never reused with the same key.

For the key, each device owns an RSA key pair with a 2048-bit modulus, generated in the browser. The content key is wrapped with RSA-OAEP using SHA-256 \cite{rfc8017}. According to formula (2.1), the wrapped key for device $j$ is computed as follows:
\begin{equation}
W_j = \mathrm{RSA\text{-}OAEP}_{\mathrm{SHA\text{-}256}}\left(PK_j, K\right),
\label{eq:wrap}
\end{equation}
where $W_j$ is the content key wrapped for device $j$; $PK_j$ is the public key of device $j$, registered in SPKI format; $K$ is the 256-bit content key of the secret.

According to formula (2.2), the envelope that the browser sends and the server stores is the following tuple:
\begin{equation}
E = \left(r,\ \{(d_j, W_j)\}_{j=1}^{n},\ IV,\ C\right),
\label{eq:envelope}
\end{equation}
where $E$ is the envelope stored in Redis; $r$ is the user name of the recipient; $d_j$ is the identifier of the $j$-th device of the recipient; $W_j$ is the content key wrapped for that device according to formula (2.1); $n$ is the number of active devices of the recipient; $IV$ is the 96-bit initialisation vector; $C$ is the AES-GCM ciphertext including its authentication tag. None of these values allows the server to recover the plaintext without a private key, and the private keys never leave the browsers. The lifetime is not part of the envelope; it is stored by Redis as the expiry of the key.

The identifier of a secret is generated on the server by \texttt{secrets.token\_urlsafe(32)}, which encodes 32 bytes from the operating system's random source in 43 URL-safe characters. According to formula (2.3), the probability that an attacker guesses any of the stored identifiers in a series of attempts is bounded as follows:
\begin{equation}
P \le \frac{N \cdot q}{2^{256}},
\label{eq:guess}
\end{equation}
where $P$ is the probability of a successful guess; $N$ is the number of secrets stored at the same time; $q$ is the number of guesses; $2^{256}$ is the number of possible identifiers. Even with a million stored secrets and the rate limit of 30 attempts per minute sustained for a century, $P$ stays below $10^{-61}$, so guessing is not a practical attack.

Single delivery rests on the burn script in Listing~2.1. Redis executes a Lua script atomically, without running other commands in between \cite{redislua}, so reading the envelope, comparing the recipient and deleting the key form one indivisible step.

\noindent\begin{minipage}{\textwidth}
\begin{lstlisting}[language={[5.2]Lua}, caption={Atomic recipient-checked burn script}, label={lst:burn}, captionpos=b]
local payload = redis.call('GET', KEYS[1])
if not payload then
  return {'missing'}
end
local ok, envelope = pcall(cjson.decode, payload)
if not ok or type(envelope) ~= 'table' or envelope['recipient_id'] ~= ARGV[1] then
  return {'denied'}
end
redis.call('DEL', KEYS[1])
return {'burned', payload}
\end{lstlisting}
\end{minipage}

Two simpler designs were rejected. Reading and deleting with \texttt{GETDEL} before checking the recipient destroys the secret when the wrong person asks for it; this was the behaviour of an early version and is described in Chapter~3. Reading with \texttt{GET}, checking in Python and then deleting with \texttt{DEL} lets two parallel requests of the recipient both read the envelope before either deletes it.

The design is summarised by five invariants that the tests in Chapter~3 verify. The source code refers to them by the numbers of the team's internal specification, which are kept so that a reader can follow the references.

\section{Implementation and Security Verification}

This chapter describes how the design was implemented, which security controls protect the implementation, how the controls were tested and delivered, and which problems were discovered and solved during the internship. Each security control is presented in the form required by the DAS brief: the problem it addresses, its implementation, its testing and its limitations \cite{dasbrief}.

\subsec{Implementation of the Web Client and the API}

The web client is a Next.js 15 application with a single main page. Its cryptographic functions are collected in the module \texttt{lib/crypto.ts}, which uses only the browser's Web Cryptography API and has no third-party cryptographic dependency. Key generation, public key export in SPKI PEM format, AES-GCM encryption and decryption, and RSA-OAEP wrapping and unwrapping are separate functions; the encryption routine is shown in Appendix~C. The module \texttt{lib/key-store.ts} stores the device key pair in IndexedDB under the database \texttt{secretshare\_keystore}, indexed by the user name, so that two users who share a computer do not share keys.

After a successful sign-in the page looks up the stored key pair. If there is none, it generates a pair, stores it and registers the public key; the returned device identifier is stored next to the pair. When a secret is created, the page builds a share link of the form \texttt{/?id=<payload\_id>} and offers a copy button. When a page is opened with such a link, or with the identifier in the fragment \texttt{/\#<payload\_id>}, the page starts the existence check automatically and, if the secret exists, shows the burn warning described in Section~2.2. After a successful reveal the identifier is removed from the address bar.

The API is a FastAPI application written in Python 3.12. All configuration is read by one Pydantic settings class from environment variables; no other module reads the environment. The settings class validates the configuration at start-up: it rejects lifetime bounds that contradict each other, malformed proxy address ranges and, in production mode, missing database or identity provider settings. Database migrations are applied by Alembic when the container starts, and a failed migration stops the container.

Errors are mapped centrally. A missing, burned or expired secret always produces the same 404 response, and there is deliberately no separate error for expiry, because a different answer would tell an attacker that a secret once existed. An unavailable Redis produces 503 with a \texttt{Retry-After} header. Validation errors produce 422 without the rejected input, so that a malformed request containing a secret is never echoed back or written to a log by a client.

Three pieces of middleware wrap the application. The body size middleware checks the declared length and counts the bytes actually received, and stops a request that exceeds 64 KB with status 413 before the body is parsed. The trusted proxy middleware accepts \texttt{X-Forwarded-For} only from configured proxy address ranges and takes the right-most untrusted address as the client, because the left-most entry is written by the client and can be forged. The header middleware sets \texttt{Cache-Control: no-store}, \texttt{X-Content-Type-Options}, \texttt{X-Frame-Options}, \texttt{Referrer-Policy: no-referrer} and a restrictive Content Security Policy on every API response.

Rate limiting uses a fixed one-minute window per client address, stored as counters in Redis: 10 creations and 30 existence or reveal requests are allowed per minute, and further requests receive 429 with a \texttt{Retry-After} header. If Redis is unavailable, the limiter lets the request through and logs a warning, so the protection degrades before the service does.

An implementation detail concerns the registration of keys. The envelope format allows a secret to be encrypted for several devices, and the sender's browser wraps the key for every active device it receives. The current registration endpoint, however, revokes the previous active key of the same platform whenever a new one is registered. In practice a user therefore has one active web device at a time: the browser in which the user signed in most recently. This keeps the key registry small but means that a secret sent before a user changes browser can only be read in the previous browser; the consequences are discussed in the Conclusions.

The first control is the result of a vulnerability that the team found in its own code. An early version served secrets at \texttt{GET /secrets/\{id\}}, and during end-to-end testing the full 43-character identifier appeared in the Uvicorn access log, next to an audit table that carefully stored only 8 characters. Anyone with access to the logs or their backups could have read unconsumed secrets. The identifier was moved into the request body, which no access log records, and a logging filter was added as a second layer for old bookmarked links and for exception messages. This follows the general guidance that logs must not contain session identifiers, access tokens or sensitive data \cite{owasplogging}.

The Content Security Policy addresses the risk identified in Table~1.1: a script injected into the page could read the plaintext before encryption, which would defeat the whole design. The policy allows only scripts that carry a nonce generated for the current response, forbids plugins and framing, and restricts all connections to the same origin, which is possible because Traefik serves every component under one host \cite{csp3}. The test replays the real policy over a page containing an injected script and confirms in a headless Chromium browser that the script does not run and that a violation event is raised.

The uniform authentication error closes an information leak in the token validation. Originally the 401 response contained the message of the underlying library, such as an unknown key identifier or an expired signature, which told an attacker which part of a forged token was wrong. Every rejected token now receives the same message, and the reason is written only to the server log, without the token itself. Error messages that reveal internal details are a typical example of the weaknesses listed by OWASP \cite{owasptop10}.

Several controls are known to be incomplete, and the team documented them as such rather than claiming them as finished:
\begin{itemize}
  \item the append-only trigger can be disabled by the database owner, and the API currently connects as the owner;
  \item the audit log stores IP addresses and user agents, which are personal data under the GDPR, but no retention period or deletion job exists yet \cite{gdpr};
  \item the Content Security Policy still allows inline styles, which are produced by the current interface code;
  \item the TLS clients verify the certificate chain but not the host name of Redis and PostgreSQL;
  \item Redis requires neither a password nor a client certificate, so any container on the internal network can read envelopes;
  \item the web share link carries the identifier in the query string, so the web tier receives it in the request line, although it does not log it by default and the page removes it after reading;
  \item response timing was not measured, so differences in processing time could still distinguish some cases that the responses themselves hide.
\end{itemize}

The CSP tests use the built-in Node.js test runner and are not yet part of the pipeline; they were run locally against the production Docker image.

The preview environments proved to be one of the most useful tools of the project. Every pull request receives its own copy of the whole system, reachable over HTTPS at a host name derived from the pull request number, so reviewers can test sign-in, encryption and the burn flow in a real browser before merging. The per-preview host name is also a technical necessity: the Web Cryptography API requires a secure context, and each preview needs its own redirect address registered in Keycloak.

\subsec{Challenges Encountered}

Several of the most instructive results of the internship were problems that the tests or the preview environments revealed. They are summarised here because each of them changed the design or the process.

The first problem was that a wrong recipient destroyed the secret. In an early version the reveal handler removed the envelope with \texttt{GETDEL} and only then compared the recipient. A user who opened a link meant for someone else received the expected 403 response, but when the real recipient opened the link, the secret was gone. The defect was reproduced with two accounts and fixed with the Lua script in Listing~2.1. The regression test now starts ten requests of a wrong user in parallel with ten requests of the recipient against a real Redis and asserts that exactly one request receives the secret and that it is one of the recipient's.

The second problem was the identifier in the access log, described in Section~3.2. It showed that a protection applied in one place, the truncated audit prefix, can be defeated by a component that the developers do not think of as storage, and it led to the rule that identifiers never appear in a URL of the API.

The third problem was an empty audit log. Everything appeared healthy and the smoke tests passed, but the \texttt{audit\_events} table did not exist in the preview and staging databases, because no step applied the migrations. The audit service ignores write errors by design, so that an audit outage cannot change the answers to secret requests, and the failure was therefore invisible. Migrations are now applied when the container starts, and the case shows that a deliberate fail-open decision must be paired with monitoring.

The fourth problem was a pipeline that reported success without running its tests. The preview deployment sent its script to the server over SSH through standard input, and a \texttt{docker compose exec} command inside the script read the rest of the script as its own input. The shell then reached the end of its input and exited with success before any smoke test had run, and the smoke tests had in the meantime become outdated without anyone noticing. The fix redirects the input of such commands and makes the step fail unless the log contains the final success message of the test battery.

The fifth problem concerned rate limiting behind proxies. All users of an environment shared one limit of ten creations per minute, and the audit log recorded the address of Traefik instead of the client, because the API saw every request as coming from the proxy. The trusted proxy middleware described in Section~3.1 solved the problem. The team also documented the pitfall that trusting the left-most \texttt{X-Forwarded-For} entry would let any client choose a new address for every request and bypass the limit.

The sixth problem appeared when the preview environments moved to HTTPS. Sign-in failed with an issuer mismatch, because Keycloak advertised its issuer as \texttt{https://<host>:80/keycloak/...}: Tailscale terminated HTTPS on port 443 and passed plain HTTP to Traefik on port 80, and Keycloak combined the forwarded scheme with the forwarded port. Since OpenID Connect clients must reject tokens whose issuer differs from the configured one \cite{oidccore}, the failure was correct behaviour of the client. It was fixed by making Traefik forward port 443 explicitly and by configuring the public host name of Keycloak for each preview.

A common lesson of these cases is that security properties must be tested end to end in an environment that resembles production. Each of the five problems passed unit tests at some point and was found only through an integration test, a preview deployment or a look at real logs.

\unnumberedsection{CONCLUSIONS}

The domain analysis showed that credentials shared through chat and ticket systems remain exposed for years and that existing one-time-link services leave at least one of four weaknesses open. From it the team derived a concept in which the server is blind, access is bound to the recipient's identity, delivery is atomic and nothing secret is logged. The system design expressed the concept as nine functional and ten non-functional requirements, modelled the behaviour and structure in UML and summarised the security properties as five invariants that can be tested.

The main achievements of the internship are the following:
\begin{itemize}
  \item a working minimum viable product in which secrets are encrypted in the browser with AES-256-GCM and RSA-OAEP and the server stores only ciphertext;
  \item recipient authentication with Keycloak through OpenID Connect and PKCE;
  \item atomic, recipient-checked single delivery implemented as a Lua script in Redis;
  \item removal of secret identifiers from API request lines and logs, found and fixed through the team's own testing;
  \item an append-only audit log that stores no secret material and does not affect the responses of the relay;
  \item internal TLS to both data stores, a Content Security Policy for the page that performs encryption, and uniform error responses;
  \item a pipeline with 176 automated API and security tests, TLS and live OAuth tests, and a preview environment for every pull request.
\end{itemize}

The work also produced a clear list of limitations, which is at the same time the plan for the PBL semester from October to December:
\begin{itemize}
  \item the client should send its device identifier on reveal so that the server refuses, without burning, a request from a device that cannot decrypt the secret;
  \item device private keys should be generated as non-extractable keys;
  \item the public key lookup should require authentication to prevent enumeration of user names;
  \item multi-factor authentication and brute-force protection should be enabled in Keycloak, as required by the DAS brief;
  \item the API should connect to PostgreSQL with a role that does not own the audit table, and audit rows should be copied to append-only storage;
  \item a retention period and a deletion job for audit data should be defined to comply with the GDPR;
  \item share links should use the URL fragment instead of the query string;
  \item inline styles should be moved to the stylesheet so that the Content Security Policy can forbid them;
  \item the staging deployment, which currently fails, should be repaired, and an incident response plan should be written.
\end{itemize}

For the implementation phase, the data model already allows users from chat platforms such as Slack and Microsoft Teams, and a sender dashboard would let users revoke unread secrets.

In summary, the internship established a secure foundation for SecretShare: its central security properties are implemented, tested and documented together with their limits.

\startappendix{C}{Browser Encryption Source Code}

The following functions from \texttt{web/lib/crypto.ts} encrypt a secret and wrap the content key, as described in Section~2.4. They use only the Web Cryptography API of the browser.

\begin{lstlisting}[language=TypeScript, caption={Encryption of the secret with AES-256-GCM}, label={lst:aes}, captionpos=b]
export async function encryptAesGcm(plaintext: string): Promise<{
  ciphertext: string
  iv: string
  rawAesKey: ArrayBuffer
}> {
  const rawAesKey = window.crypto.getRandomValues(new Uint8Array(32)) // 256-bit key
  const iv = window.crypto.getRandomValues(new Uint8Array(12)) // 96-bit IV

  const aesCryptoKey = await window.crypto.subtle.importKey(
    'raw', rawAesKey, { name: 'AES-GCM' }, false, ['encrypt']
  )
  const encodedPlaintext = new TextEncoder().encode(plaintext)
  const cipherBuffer = await window.crypto.subtle.encrypt(
    { name: 'AES-GCM', iv }, aesCryptoKey, encodedPlaintext
  )
  return {
    ciphertext: arrayBufferToBase64(cipherBuffer),
    iv: arrayBufferToBase64(iv.buffer),
    rawAesKey: rawAesKey.buffer,
  }
}
\end{lstlisting}

\begin{lstlisting}[language=TypeScript, caption={Wrapping of the content key with RSA-OAEP}, label={lst:wrap}, captionpos=b]
export async function encryptAesKeyWithRsa(
  rawAesKey: ArrayBuffer,
  rsaPublicKey: CryptoKey
): Promise<string> {
  const encryptedKeyBuffer = await window.crypto.subtle.encrypt(
    { name: 'RSA-OAEP' }, rsaPublicKey, rawAesKey
  )
  return arrayBufferToBase64(encryptedKeyBuffer)
}
\end{lstlisting}
